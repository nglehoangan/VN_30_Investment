# Formal scoring handoff for an existing research closure

Use this when a single ticker already has a closure or when resuming a blocked `prepare`. Work from the latest verified receipts for the same ticker, economic cutoff and purpose. Reopen an economic conclusion only for a specific material defect. Preserve approved bands, N/R, rubric weights and the original evidence.

1. **Check data consumption once.** Resolve the admitted dataset through the registered sector adapter using the pinned reference and its binding knowledge date. Verify the acceptance receipt, lineage, scope and canonical dataset hash against the actual reader output. Keep the economic cutoff, source publication date and binding/evaluation time distinct. A replay mismatch, missing route or schema error is a technical defect. For BANK data, use the approved requirement version for the ticker and preserve declared capital concepts. For effective share changes supported by later disclosures, use only an approved retrospective branch and retain both dates.
2. **Assemble the actual scorer packet.** Map each rated rubric to every required topic in `RUBRICS`, with resolvable evidence IDs. Verify the exact authorized N/R set, metric dispositions, and dated M1 evidence and adoption. Use the existing methodology and calculator in a rehearsal. Separate a missing topic binding from missing economic evidence. Mark scope or M1 approval pending only where the applicable verifier requires it.
3. **Validate before requesting an executable signature.** Derive pins from the actual bytes or canonical objects using the production helpers. Check SHA-256 format and equality against a read-only adapter replay. In a quiet SQLite copy, exercise the executable against the same dataset, adapter, scope and assessment. If owner authorization prevents end-to-end preflight, run the available component checks and identify the gate still untested. Keep the accepted bytes stable. A changed executable digest requires its own exact approval, and any changed review binding requires review verification against the successor packet.
4. **Seal both reviews against the final input.** Use the trusted verifier for `PREPARATION` and `CHALLENGE` with the final evidence, methodology and M1. Record actual review times and the authorized review mode. Apply the verifier's chronology rules without changing the economic cutoff. Preserve the owner's exact message and use the contract's normalized approval line for machine comparison when Markdown formatting is present. Reuse prior checks where their inputs match.
5. **Run the governed CLI and resume from the first failed check.** From the repo root use `python3 -B tools/scoring/vn30_score.py --ticker <ticker> --mode prepare --universe-version <version> --cutoff <date> --candidate <path>`. Keep one current record with the exact failure, supporting evidence, and the next action. Fix the failed layer and rerun its check before repeating full preflight. On `READY_FOR_CIO`, retain the proposed route and return the actual execution statement `Approve exact single-ticker VN30 score <approvalHash> for <ticker> at <date>`. Use the emitted `approvalHash` for the statement and retain `preflightHash` with the route.
6. **Execute the exact route and retain the result.** Once approved, register the route in the intended authorized environment. Replace a matching unsigned draft there rather than appending a duplicate. Run `check`, then `score`; consult `status` and use the existing `resume` path for a previously started matching job. Read back the stored artifact and verify its envelope hash and nested scorecard hash separately. Retain the exact bytes outside a disposable database, the execution receipt and the current checkpoint. Report the environment explicitly and pass the verified subject to the separate publication workflow.

The TCB case showed why these checks matter. A 62-character expected dataset digest stopped an already signed executable, draft review pins did not satisfy the final verifier, and successful isolated scoring still required a separate website release. Resolve dates, capital inputs and coverage from each ticker’s approved scope.

When a bounded [evaluation feasibility audit](../../../docs/03%20SCORING/STRUCTURAL_EVALUATION_GAPS_v1.0.md) accompanies Prepare, run the companion entry point with the same ticker, universe, cutoff and candidate. Use the original native Prepare fields for route readiness, approval and preflight hashes. Keep the reviewed audit packet as the feasibility record.

## Public-data route handoff

Bind the reviewed route, source operands and counterevidence to the one-ticker assessment. Reuse reviewed dispositions for optional metrics and record a precise reopening trigger for N/R. For PX04, retain action comparability whenever per-share, action-sensitive or materially scope-affected economics enter the assessment. Consult the [Approved Baseline v1.0](../../../docs/03%20SCORING/PUBLIC_DATA_PROXY_SPECIFICATION_23_RUBRICS.md) before preparing the exact executable and review bindings.
