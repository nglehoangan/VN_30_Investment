# Dividend receivable settlement — proposed versioned extension

Assessment date: 2026-10-27 (Asia/Ho_Chi_Minh). Phase 1 design/evidence closure only. Owner approved the prior architecture assessment as baseline v1.0 in the current task; this is not authenticated source/identity acceptance or Phase 2 authorization. Original baselines and sealed evidence remain unchanged. SOURCE_REFERENCES.json pins inspected files; JSON Pointers below address those pinned bytes.

Existing transaction.ts:74–109 handles external cash and DIVIDEND_CASH. Ordinary DIVIDEND_CASH posts cash and reconstruct.ts:99–102 records dividend income; it does not clear a prior claim. TRADE_SETTLEMENT:90–104 requires original BUY/SELL and a specifically referenced obligation. `settlesId` is currently forbidden for any other type. Neither is a safe imported-dividend-claim settlement. M2 DATA_MODEL §6 dividend cash baseline explicitly leaves an optional receivable lifecycle as a later extension.

Propose **DIVIDEND_RECEIVABLE_SETTLEMENT v1**, a new explicit event contract, not changed meaning of historical DIVIDEND_CASH or TRADE_SETTLEMENT. Keep numeric/MWAC method identity unchanged; separately version event schema/dispatch so legacy facts and ordered legs rebuild byte-for-byte. Before implementation, approve how schema version is carried (facts envelope + method registry compatibility); do not silently tag old records v2 or relax exact equality checks.

Required immutable fields: portfolio ID, event UUID, idempotency key, schema version, issuer/security identity evidence, corporate-action/entitlement ID, **original transaction ID and RECEIVABLE leg ID**, allocated claim identity and amount, receipt source namespace/hash/path/row or JSON Pointer, original broker event/reference, receipt effective date/time precision, knowledge/retrieved/recorded timestamps, accepted evidence references, exact decimal amount/currency, settlement accounting representation, correction links. Hash a canonical manifest including references and scope. Hash is integrity, not authority.

Opening570k is one aggregate claim: before any partial clearing, attach a separately accepted, immutable **allocation record** pointing to original leg and proven GAS/MWG components summing exactly570000. This metadata does not create more assets/legs/income. Subclaim balances are allocation minus linked settlements/reversals; child sums must equal parent residual. Without exact allocation/evidence, BLOCKED; no ticker/amount-only matching.

Net-claim mode: original recognized net claim R, accepted receipt c>0; emit CASH+c, RECEIVABLE−c referencing the original leg/subclaim; externalFlow NONE, quantity/basis/realized/net-new-income all0. Enforce c ≤ remaining eligible subclaim and remaining parent. Full settlement residual0; partial settlement residual>0; currency/portfolio/issuer/action match. No negative residuals, no cash recorded twice from both cash import and this event. Example synthetic95k net claim,40k then55k leaves55k then0; third1 rejected. Actual MWG95k remains unposted.

Gross-claim mode requires independent evidence original grossG and taxT: cashG−T plus evidenced tax treatment and claim−G, equation netCash + withheldTax = clearedGrossClaim; net assets fall only by the evidenced tax expense. Tax expense occurs once only if not already recognized; a net claim must not be cleared by grossG. If gross tax unknown, net settlement may qualify only when the original claim is evidenced net; gross/tax analytics UNKNOWN. A gross/net mismatch blocks, never a guessed conversion. A new income entitlement requires a separately approved recognition event; imported opening income must not be recognized again.

Effective time is actual cash availability with source precision; knowledge is retained witness time, never retroactively upgraded. Date-only ambiguity with same-day events must be resolved or bounded, not fabricated. Prospective events after opening only. For AS_KNOWN queries require evidence knowledge≤cutoff; retrospective reconstruction is separately labelled.

Idempotency identity binds portfolio+provider immutable event+receipt row allocation+claim+schema. Byte-identical retry returns original result; same identity/different content conflicts. Content hashes supplement stable broker references (row order changes cannot permit duplicates). An economic receipt registry prevents double classification as DIVIDEND_CASH/CASH_DEPOSIT/settlement across files/captures; split partial allocations across claims must sum to the one receipt without overlap.

Correction appends linked reversal and replacement, never edit original. Reversal cash−c/claim+c, income0 and flow0; fail if downstream cash obligations cannot remain funded. Reverse dependent allocations/settlements in one approved correction group when needed, preserving earlier as-of states. Revalidate every affected boundary and future posted activity. Original recognition cannot reverse while active settlements remain unless linked corrective group restores consistency. Receipt re-import after reversal is not a fresh duplicate; explicit corrected lineage required.

Concurrency: source dedup, claim residual check, receipt allocation reservation, expected revision CAS, business legs, audit event and idempotency result must commit atomically or all rollback. Existing repository provides transaction/CAS/leg posting, **not a verified atomic governance audit integration**. No successful post claim until audit persistence is connected and tested. Failed projection rebuild remains STALE, authoritative posting must not repeat. No-login configuration does not authorize authenticated approval; no JSON/OS-user/Codex substitution.

No new production code, event, migration, claim allocation or acceptance is created in Phase1.
