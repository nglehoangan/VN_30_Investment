# Calculation rules — specification only

2026-10-27 · Phase 3.1 DESIGN PROPOSAL ONLY. No calculator, adapter, schema validator, snapshot store, migration, acceptance artifact or Phase 3.2 implementation is created. Proposed amendments require explicit owner review.

No calculation is implemented/executed in Phase3.1. Future pure arithmetic consumes an already qualified immutable plan; it never posts transactions or reconstructs a second book.

1. Reuse approved Decimal12 fixed-point/half-even division rules. Parse exact strings; VND only. Reject unsupported precision/range/malformed amounts, nonpositive quotes and fractional ordinary shares. No JSfloatingpoint financial arithmetic. Preserve quote units/native lexemes; normalization factor must be qualified, not inferred from amount/tradeUnit.
2. For every distinct accepted economic unit: marketValue = quantity×qualifiedRAWprice. Ordinary quantities come from existing reconstructPortfolio atT/revision. Partitioning status never increases aggregate quantity. Split/merger/rights effects must already be posted with accepted terms or fullNAVblocks; no calculator quantity fix or adjustedprice workaround.
3. Cash = sumpostedcashlegs atT. Receivables = trade + other disjoint recognized residuals. Liabilities = tradepayables + other recognized debt/fee/tax obligations, with no overlap. Existing state.receivables/payables already aggregate obligations: do not add an extra breakout again. No off-ledger broker fee/debt overlay or manual balance plug.
4. Sum all held-unit values exactly, addcash/claims and subtractliabilities exactly. Reject unrepresentable product/intermediate/final via approved precision/range validation; never round a captured input to pass. Store authoritative result exact; presentation rounding is separate proposed display policy, not a rewritten accounting value. Division for weights only under existing numeric contract and positive denominator; weights are not action permissions.
5. Verify coveredunits = heldunits, partition sums = ledger quantities, no economic entitlement/leg in two buckets, claims/receipt allocations conserve original residuals, and cash/quantity/obligation reconciliation satisfies accepted scope. Missing/contradictory required component keeps fullresultnull. Explicit subtotal excludes named unknowns and is not a bound, NAV or official metric.
6. Known negative/zero NAV is not clamped to0 or hidden as missing if all components are otherwise valid; return exact amount plus NONPOSITIVE_NAVriskalert. Ratios/return denominators requiring positive capital becomeunavailable. This grants no margin/borrowing permission; existing accounting no-margin rules still apply.

Use valuePortfolio only on a compatible all-ordinary plan after qualification and with all obligations truly represented. Its latest-observation selector must not decide source/session eligibility: pass exactly one already-selected qualified observation per heldunit. With pending/different rights or missing nontrade-liability representation, block rather than mutate PortfolioState or append artificial price IDs. If an adapter cannot preserve economic/time semantics, use the same Decimal primitives for the pure NAVcomponent expression under new contract, not another transaction engine. Do not expose its basis-derived unrealized/inceptionP&L when those are unqualified.
