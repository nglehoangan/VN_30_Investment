# Qualified Market Price proposal

2026-10-27 · Phase 3.1 DESIGN PROPOSAL ONLY. No calculator, adapter, schema validator, snapshot store, migration, acceptance artifact or Phase 3.2 implementation is created. Proposed amendments require explicit owner review.

Proposed `qualified-market-price-v1` is a **future verified output**, not an accepted-price JSON file or provider installed now. Each price binds:

- Exact ledger security ID + namespace; market namespace/UUID, provider stable instrument code, ISIN or approved alternate continuity evidence, venue and security class. Ticker is display only; local market UUID is not a provider-issued UUID.
- Exact positive decimal price, VND, VND_PER_SHARE, multiplier1; original decimal lexeme/native unit and lossless normalization/version. tradeUnit is not a scaling instruction.
- priceKind = OFFICIAL_CLOSE / PROVIDER_EOD_CLOSE / CURRENT_TRADE / LAST_AVAILABLE_CLOSE / HISTORICAL_CLOSE / UNQUALIFIED_INDICATIVE. Initial qualified NAV accepts only the explicitly authorized completed-EOD kind and finality scope. Provider bar/board agreement is not automatically an official exchange close.
- Exchange-local tradingDate/session, finality/completed-session proof; providerPriceAt nullable, timestampOrigin and precision; policy-normalized sessionBoundaryAt distinct from actual provider timestamp; retrievedAt, knownAt, normalizedAt. Unknown provider tick/publication time staysnull; no fabricated15:00provider timestamp.
- Immutable source/publisher/source-contract/schema/capture request/raw path+SHA256+JSONPointer, source authority scope, accepted identity/CA policy and evidence hashes; qualification/independent acceptance/owner release refs, effective/knowledge intervals, expiry/revocation heads, and price revision.
- Accepted calendar/session policy identity, eligibility window, freshness result CURRENT_FOR_DECLARED_SESSION / STALE_SESSION / UNKNOWN_SESSION / CONFLICTING / UNQUALIFIED; all held-security coverage hash and quantity-basis binding.

Source authority and independent verifier must authenticate exact evidence content/purpose. Hash integrity, signed-in user, broker reputation, template FORMAL and code tests alone do not establish accepted financial evidence. Reuse existing TCBS acquisition/normalization and retained byte verification after authorization; no second API client.

Calendar: independently accepted HOSE calendar, holidays/weekends/exceptional closures and bounded coverage; outside2026candidate range UNKNOWN. Latest completed session is selected by accepted boundaries, not Ncalendar-days age. Window ends at next qualified session completion (half-open proposal). Legacy inclusive-through maps only under accepted millisecond resolution to nextBoundary−1ms; no arbitraryTTL. Existing eodPolicy permits **VALUATION only**, despite PORTFOLIO_NAV existing in MarketPurpose union. A new purpose-specific accepted policy/capability is required, not copying the old proof.

Before today's session completes, preceding session may be latest completed; weekends/holidays may span civil days. After next completion, yesterday's capture is stale even if new capture failed. Missing calendar/session/finality or conflicting closes blocks; no older-price fallback. Suspended/no-trade instrument is not fixed by exchange-open calendar; initialv1 blocks without separately authorized exception methodology. RAW is required with actual ledger units. ADJUSTED/history prices are not interchangeable. Corporate-action effective dates and actual quantity replay must align; no guessed ratios/discounts, transaction-price close, current-price backfill or estimated zero.

Proposed explicit acceptanceStatus: MISSING / UNVERIFIED / ACCEPTED_FOR_DECLARED_NAV_SCOPE / EXPIRED / REVOKED, only on a future authenticated verified-price DTO, not existing offline placeholders. Operational values are not created here. Keep parent capture status PARTIAL_CAPTURE unchanged; any later purpose-limited EODsubset acceptance must bind exact subsetmanifest/hash and exclusions, never relabel the entirecapture complete or grant accounthistory/source/scoring authority. Financial report source policy is not a marketNAVgrant and remains unchanged.

Duplicate handling proposal: byte/economic-identity-equivalent repeats of the same immutable price revision may be deduplicated while retaining every source variant. Distinct sources/revisions require an accepted canonical source-resolution rule; matching amounts alone cannot establish same session/adjustment/finality. Disagreement or unresolved ambiguity blocks rather than averaging/latest-wins. Same-provider bar/board consistency is technical corroboration, not producer-distinct independent acceptance.
